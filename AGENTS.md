# Instructions for coding agents

Fretium is a browser-based fretboard diagram generator.

## Workflow

### Defaults

- Use `pnpm` for all commands.
- Keep edits minimal and focused on the user request.
- Prefer targeted checks during iteration; run full validation right before finish.

### Testing

- Always run tests with `--run` to avoid watch mode:

  ```sh
  pnpm test --run
  ```

- When iterating on a specific test file, run only that file:

  ```sh
  pnpm test --run path/to/file.test.ts
  ```

- For type-level test assertions, use Vitest's typechecking infrastructure with
  `.test-d.ts` files and `expectTypeOf`/`assertType`, wrapped in normal Vitest
  `test(...)` (or `describe`, `it`, etc.) blocks, rather than adding TSC-only fixtures or
  `@ts-expect-error` probes to runtime test files.

- Use per-file runs during tight iteration loops, then run the full suite in final validation.

### Fast iteration loop

Run only what is needed while developing:

- TypeScript/runtime changes: `pnpm lint:tsc`
- Pure logic changes: `pnpm test --run path/to/file.test.ts`
- React component or hook behavior changes: `pnpm test --run path/to/file.test.tsx`
- Lint/style-sensitive changes: `pnpm lint:eslint` and/or `pnpm lint:prettier`
- Dependency/unused-export-sensitive changes: `pnpm lint:knip`
- Import graph/module structure changes: `pnpm lint:madge`
- SCSS changes that affect generated typings: `pnpm build`
- Behavioral changes: `pnpm test --run path/to/file.test.ts` while iterating, then `pnpm test --run` before completion

### Final validation (required)

Before completing a task, run all of these unless the task was purely non-code (e.g. documentation):

```sh
pnpm lint:tsc
pnpm lint:eslint
pnpm lint:prettier
pnpm lint:knip
pnpm lint:madge
pnpm test --run
pnpm build
```

### CSS `.d.ts` files (autogenerated)

NEVER edit the generated `.d.ts` files in `src/`.

If a CSS module typing needs to change, edit the corresponding `.scss` file and run `pnpm build` to regenerate the `.d.ts` file. This also applies when TypeScript reports errors caused by stale generated CSS typings, such as `noPropertyAccessFromIndexSignature` issues.

## Coding style

### Project structure

- Key folders:
  - `src/components/` contains React UI, with feature-specific helpers/tests/styles colocated under the owning component folder when that keeps the feature easier to reason about.
  - `src/hooks/` contains reusable React hooks that are not specific to a single component or feature.
  - `src/lib/` contains framework-agnostic application logic; prefer putting pure logic here instead of inside components when it is reused or independently testable.
  - `src/config/` contains static instrument and pattern configuration data.
  - `lib/` at the repo root is for small shared helpers that are not specific to the app runtime.
- Preserve the existing colocated feature layout instead of centralizing unrelated helpers into broad utility files.
- Keep non-UI business logic out of React components when it can live in a hook or a pure module.

### Comment style

- Do not include too many comments, but also do not leave the code uncommented if it is not self-explanatory. Use your judgment to find a good balance.
- It is important that you document gotchas and small details that are not obvious from the code itself. Always try to document the **"why"** and not just the "what" of the code. For example, this comment is not bad, but also not ideal:

  ```ts
  // +1 to account for the 12th fret
  drawFrets(TOTAL_FRETS + 1);
  ```

  This is a better comment:

  ```ts
  // +1 because we want to see the 12th fret so it's easier to see both the open
  // position and the 12th fret position of the same note, which is especially
  // useful for learning and memorization
  drawFrets(TOTAL_FRETS + 1);
  ```

- Functions should usually have TSDoc comments, especially if they are exported or not trivial. For very small and trivial functions, a comment may not be necessary.

### CSS styling

- Always try to use `.module.scss` files instead of inline styles or `style` props for styling. At most use inline styles for very specific, one-off cases where it would be more cumbersome to create a CSS class (e.g. dynamic widths or heights, CSS vars injection, etc.)
- When a styling change is broadly useful across the app, move it into shared styles such as `src/index.module.scss` instead of keeping it scoped to a single component. For example, styles for `<select>`, `<input>`, etc. should be in shared styles since they are used across the app, and it would be cumbersome to have separate styles for each component that uses them.
